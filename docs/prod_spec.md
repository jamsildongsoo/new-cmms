# CMMS 제품 명세

업무 규칙과 화면 기준을 정의한다. 구현 구조는 [기술 명세](tech_spec.md), 설치·운영은 [설치 가이드](install_guide.md)를 따른다.

## 1. 서비스 범위

회사별 조직·사용자·설비·보전·구매·재고 업무를 관리한다. 전자결재, 첨부, 게시판을 공통 기능으로 제공한다. 서버는 외부 PostgreSQL과 연결하며 업로드 파일은 애플리케이션 서버에 저장한다.

현재 하나의 애플리케이션은 하나의 DB를 사용하고 업무 데이터를 회사코드로 논리 분리한다. 고객별 DB 배포 시에는 DB 계정·JWT 비밀키·업로드·백업도 고객별로 분리한다. 단일 서버에서 요청마다 고객 DB를 선택하는 기능은 제공하지 않는다.고객별 DB에 고객 산하 계열회사를 관리하고, 고객이 다른 경우 DB를 분리한다.


## 2. 메뉴와 화면

| 순서 | 그룹 | 메뉴 |
|---|---|---|
| 1 | 홈 | 업무 진입 링크 |
| 2 | 전자결재 | 결재문서 |
| 3 | 게시판 | 게시글·댓글 |
| 4 | 보전관리 | 설비 마스터, 예방점검, 작업의뢰서, 작업 오더, 허가요청서, 작업허가서 |
| 5 | 구매·재고관리 | 자재 마스터, 벤더, 창고, 구매요청, 구매발주, 재고처리, 재고 현황, 수불장, 월 마감 |
| 6 | 조직관리 | 회사 정보, 사업장, 부서 |
| 7 | 사용자·권한관리 | 사용자, 역할, 권한 |
| 8 | 공통코드 | 공통코드 관리 |

- 홈·사이드바는 같은 메뉴 정의를 사용한다. 권한이 없는 메뉴는 숨기며 최종 접근은 서버에서 검사한다. 결재·게시판은 별도 모듈 CRUD 권한을 요구하지 않는다.
- 목록 상단은 `인쇄`, `신규`이며 일반 행별 Actions는 두지 않는다. 허가요청 행의 `작업허가`는 업무 연결 버튼이다.
- 개별 화면은 해당 기능에 따라 `인쇄`, `목록`, `저장`, `삭제`, `상신`을 표시한다. 재고전표는 `확정`, 허가요청은 `신청`을 사용한다.
- 시스템 문서번호는 읽기 전용이다. 신규에는 ‘저장 시 자동 생성’을 표시한다. `documentNo`는 지원하는 문서에서 사용자가 선택 입력하는 별도 관리번호다.

## 3. 인증·권한·회사 범위

- 회사코드·사용자 ID·비밀번호로 로그인한다. 인증 이후 회사·사용자·역할·소속·권한은 서버 DB 정보를 기준으로 처리한다.
- 일반 업무는 Controller의 create/read/update/delete 권한과 Service의 회사·작성자·상태 조건으로 제한한다. 결재·첨부·게시판은 CRUD RBAC 예외이며 인증과 회사 분리를 유지한다.
- 문서 범위를 적용하는 작업의뢰·작업오더·허가요청·작업허가·구매·재고전표는 회사 전체, 본인 사업장, 본인 부서와 하위 부서 중 사용자 설정에 따른다. PM과 마스터는 회사 단위다. 재고 현황·수불·마감 보고는 해당 조회 권한으로 회사 자료를 제공한다.
- 상태가 있는 문서는 작성자만 D 상태에서 수정·삭제한다. 상태 없는 마스터는 모듈 권한으로 관리한다. 게시글·댓글은 각각 작성자만 수정·삭제한다.
- 역할과 권한 배정은 회사별이다. **Permission 권한 정의는 DB 전체 공용 카탈로그**이며 권한 관리 기능의 변경은 같은 DB를 사용하는 회사에 공통으로 반영된다.
- 새로고침 시 서버에서 사용자 정보를 복원한 뒤 화면을 표시한다. 인증 만료는 재로그인하며 통신 장애는 토큰을 보존하고 재시도한다. 미저장 업무 입력은 새로고침으로 복원하지 않는다.
- 로그아웃은 브라우저 토큰·Context를 지운다. 이미 발급한 JWT를 서버에서 폐기하거나 자동 갱신하는 기능은 제공하지 않는다.

## 4. 문서와 공통 처리

- 문서 ID는 최초 저장 시 `모듈약어-YYYYMM-일련번호`로 발급한다. 회사·모듈·발급월별 증가하며 한국 시간 기준이다. 수정·상신·업무 날짜 변경으로 ID를 다시 발급하지 않는다.
- PMAINT, WRKREQ, WRKORD, PERREQ, PERMIT, PURREQ, PURORD, INVDOC, APPROV는 6자리 약어이며 게시판은 BORD를 사용한다. 일련번호는 5자리이고 월 99999건 초과 시 발급을 중단한다.
- 첨부·품목·배분·댓글 등의 내부 식별자는 UUID를 사용한다. 저장 재시도는 별도 요청 키로 중복 문서 생성을 막는다.
- 결재 연계 문서는 D(초안)→P(진행)→C(완결)/R(반려)/X(취소)다. 허가요청과 재고전표는 각각 신청·확정으로 D→C 처리한다. 별도 confirm 권한은 두지 않는다.
- 모듈 간 처리는 순차 실행한다. 결재 승인 후 원본 상태 변경 실패가 발생해도 승인 결과를 롤백하지 않는다. 관리자가 로그와 문서번호로 불일치를 처리한다.
- 감사필드는 생성·수정 시각과 사용자이며 서버가 기록한다. `deleteYn`은 감사필드와 별개다. 마스터·문서는 논리 삭제하며 공통코드 항목과 첨부 상세 등 일부 내부 자료는 실제 삭제한다.

## 5. 조직·사용자·공통코드

- 회사 정보는 본인 회사의 명칭·사업자번호·담당자·연락처·비고를 수정한다. 일반 회사 생성·삭제 API는 제공하지 않는다.
- 사업장은 회사별로 관리한다. 부서는 사업장과 독립적이며 상위 부서를 선택한다. 서버는 자기 참조를 거부한다.
- 창고 식별자는 회사+사업장+창고번호다. 사업장은 필수이며 창고 메뉴는 구매·재고관리 아래에 둔다.
- 사용자 사업장·부서·역할은 활성 선택 목록을 제공한다. 저장 시 기준정보 존재·활성 여부를 별도 재검증하지 않는다. 기준정보 삭제로 기존 사용자 소속·역할 값을 자동 변경하지 않는다. 권한 회수는 역할 권한 배정 변경이나 사용자 변경·삭제로 처리한다.
- `MATERIAL_TYPE` 같은 코드 그룹은 시스템 상수다. 별도 Code 엔티티는 없으며 CodeItem은 회사+codeId+codeItemId로 값·명칭·정렬순서를 관리한다. 같은 항목 코드도 회사별 명칭을 다르게 둘 수 있다.

## 6. 첨부

- 첨부가 없어도 첨부 영역과 빈 목록을 표시한다. disabled에서는 조회·다운로드만 제공한다.
- 파일 선택 즉시 UUID 첨부 그룹에 서버 업로드한다. 신규 문서는 refId=null로 관리하고 최초 저장 후 문서 ID를 연결한다. 첫 첨부를 위해 문서번호를 선발급하지 않는다.
- 업로드·목록 갱신 중 부모 저장·상신·확정을 막는다. 파일 추가·삭제는 문서 저장과 별개로 즉시 반영한다.
- 마지막 파일을 삭제해도 첨부 그룹은 유지한다. 미저장 문서나 DB 실패로 생기는 고아 파일은 허용하며 자동 정리하지 않는다.
- 회사·첨부 그룹을 확인한 인증 API로 파일을 제공한다. 파일 경로는 서버가 생성하며 사용자 임의 경로를 허용하지 않는다.
- 원본 연계 결재는 원본 첨부를 조회한다. 추가·삭제는 원본 화면에서 수행하며 독립 결재는 자체 첨부를 관리한다.

## 7. 보전관리

| 업무 | 주요 규칙 |
|---|---|
| 설비 | 같은 회사·사업장의 상위 설비를 트리로 선택한다. 자기·자손 참조와 순환을 거부하며 활성 하위 설비가 있으면 삭제·사업장 변경을 제한한다. |
| 예방점검 | 점검일과 설비 주기로 다음 점검일을 제안하고 사용자가 수정한다. 주기가 없으면 빈칸이다. 상세는 항목·기준값·점검값·단위다. |
| PM 상신 | OK/NOK 판정·점검부서·점검자를 확인한다. 결재 C 후 PM의 점검일·다음 점검일을 설비에 그대로 반영한다. |
| 작업의뢰 | Trouble Memo로 작성하고 전자결재로 확정한다. C 의뢰에서 작업계획을 작성할 수 있다. |
| 작업오더 | PLAN/ACTUAL을 구분한다. 계획은 C 의뢰를 선택 참조하고 실적은 계획을 선택 참조한다. 단독 작성도 가능하다. |
| WO 상세 | 공수·자재·비용을 복수 행으로 입력하며 합계를 서버 계산한다. 계획 복사·원본 첨부 조회를 제공하고 자동 재고 차감은 하지 않는다. |

예방점검 대상·허가 대상 여부와 법정점검 정보는 설비 마스터에서만 관리한다. 다음 점검일이 오늘 이전인 PM은 목록에서 표시한다. 결재 본문은 저장된 원본의 최신 내용으로 생성하며 결재 본문 편집은 원본을 변경하지 않는다.

## 8. 작업허가

- 허가요청은 신청자가 D에서 작성·수정하고 신청 시 C로 확정한다. 전자결재를 거치지 않는다.
- 담당자는 신청 완료 요청의 `작업허가` 버튼이나 단독 등록으로 허가서를 작성한다. 일반은 필수이며 화기·밀폐공간·고소·전기·양중·굴착을 추가 선택한다.
- 유형별 안전조치요구·특별요구·안전검토의견을 템플릿에서 복사하여 편집한다. 작업정보, 요구 첨부, 발급자·승인자를 저장한다.
- 작업계획서·위험성평가서의 실제 첨부를 확인하고 발급자→승인자의 한 결재선으로 상신한다. 연계 결재의 저장 버튼은 비활성화하며 상신으로 처리한다.
- 출력은 일반과 선택 특별허가서를 각각 별도 A4 한 장으로 생성한다. 각 페이지에서 개별 자필 서명을 받는다.
- 공통 작업정보, 보충허가 체크, 4열 안전요구·수기 확인, 특별요구·검토의견, 안전조치 확인/작업완료 확인의 날짜·시간·입회자·작업자, 발급자·승인자, 비고와 첨부서류를 포함한다.
- 일반의 가스 측정과 현장 확인·서명은 출력 빈칸만 제공한다. 허가 발행 시 입력값이나 전자 현장 서명으로 저장하지 않는다. 출력 길이를 초과하면 내용을 줄이도록 안내한다.

## 9. 구매

- 자재 마스터는 회사 공통이며 결재 상태 없이 관리하고 첨부할 수 있다. 거래 이력이 있는 자재는 기본단위 변경을 제한한다.
- 벤더는 구매·재고관리에서 회사별 등록·수정·논리 삭제한다. 발주는 등록된 벤더 선택이 필수이며 vendorId만 저장한다. 공급처 정보는 회사와 vendorId로 조회하므로 벤더 선택 변경 및 마스터 수정 시 최신 정보가 표시된다. 벤더 삭제 전 연결 발주 건수를 안내하되 논리 삭제는 허용한다. 삭제된 벤더도 기존 발주에서는 조회하며 신규 선택에서는 제외한다. 결재 본문은 생성 당시 내용을 유지한다.
- 구매요청은 품목·수량만 입력하고 비교 견적은 첨부한다. 단가·금액은 입력하지 않는다. 전자결재 C인 요청만 발주 대상으로 선택한다.
- 구매발주는 단독 작성 또는 복수 요청의 병합을 지원한다. 요청을 분할하지 않으며 연계 발주의 품목·수량은 변경할 수 없다. 단가는 발주에서 입력한다.
- 같은 자재는 기준 정보가 같은 경우 병합하고 allocation에 요청 품목별 출처·수량을 보존한다. 연결된 발주가 있으면 경고하되 중복 발주 자체를 금지하지 않는다.
- 요청·발주 모두 전자결재를 사용한다. 금액은 KRW이며 부가세·외화·부분입고는 제공하지 않는다.

## 10. 재고와 월 마감

| 처리 | 유형·규칙 |
|---|---|
| 입고 | 일반입고, 구매오더입고, 타사업장입고 |
| 출고 | 일반출고, 타사업장출고, 입고취소출고 |
| 이동 | 같은 사업장 내 창고 간 1단계 이동, 수량만 이동 |
| 조정 | 실사 증감, 사유 입력 |

- 재고전표는 전자결재 없이 update 권한·문서 범위·작성자 조건으로 확정한다. 음수재고는 허용하지 않는다.
- 구매입고는 C 발주 전체 품목·수량·단가를 유지하고 발주 ID를 참조번호로 기록한다. 원본에 대한 중복 확정·부분입고를 차단한다.
- 타사업장 이동은 출고→이동 중 재고→입고의 2단계다. 도착 담당자는 미입고 출고를 선택하며 전체 입고한다. 출발 금액을 보존하여 도착 사업장에 반영한다.
- 입고취소는 별도 출고 유형이다. 원 입고 금액의 자동 역분개나 발주 재입고 허용 상태 복구는 하지 않는다.
- 수량은 창고별, 수량·평가금액·평균단가는 사업장별로 관리한다. 출고는 이동평균 원가를 사용한다.
- 수불 귀속일은 postingDate이며 실제 처리 시점은 감사필드다. 같은 날짜 안의 순서는 회사별 확정순번과 품목 순서로 결정한다. 확정순번은 월별 초기화하지 않는다.
- 월 Open/Lock은 회사별이다. 복수 월을 Open할 수 있고 월 미등록·Lock 상태에서는 확정할 수 없다.
- 마감은 전월 기말을 기초로 창고 수량·사업장 수량/금액·이동 중 수불을 저장하고 Lock한다. 미확정 건수는 안내한다.
- Lock 해제·소급 처리 후 변경 월과 이후 월을 순서대로 재마감한다. 최초 마감 월의 기초는 0이다. 앞선 월이 있으면 누락 월과 전월 정상 마감을 먼저 처리한다. 월 결과는 다시 생성하여 교체한다.

## 11. 전자결재·게시판

- 결재·합의는 같은 순번 체계로 처리하고 화면 동작은 `승인`으로 통일한다. 현재 미처리 최소 순번만 처리하며 남은 결재·합의자가 없으면 완결한다.
- 참조는 처리 순번에서 제외하고 C 문서만 조회한다. 반려·부동의 의견은 선택이다. P 문서는 상신자가 취소할 수 있다.
- 본문은 Tiptap JSON으로 저장하여 서식을 유지한다. 원본 연계 결재는 저장을 비활성화하고 상신 때 저장한다.
- 게시판은 같은 회사의 사용자에게 게시글·댓글을 제공한다. 결재 상태가 없으며 게시글과 댓글 각각 본인 작성물만 수정·삭제한다. 관리자 역할도 예외가 아니다.
- 삭제되지 않은 댓글이 있으면 원문 삭제를 막는다. 본문 수정은 가능하며 모든 댓글을 각 작성자가 삭제한 뒤에는 원문 작성자가 원문을 삭제할 수 있다.
