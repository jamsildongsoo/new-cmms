# CMMS 제품 명세

업무 규칙과 화면 기준을 정의한다. 기준일: 2026-11-18. 구현 구조는 [기술 명세](tech_spec.md), 설치·운영은 [설치 가이드](install_guide.md)를 따른다.

## 1. 서비스 범위

회사별 조직·사용자·설비·보전·구매·재고 업무를 관리한다. 전자결재, 첨부, 게시판을 공통 기능으로 제공한다. 서버는 외부 PostgreSQL과 연결하며 업로드 파일은 애플리케이션 서버에 저장한다.

하나의 애플리케이션은 하나의 DB에 연결한다. PostgreSQL 인스턴스 하나에서 고객별 DB·전용 접속 계정을 분리하고 각 DB의 public 스키마를 사용한다. 고객 DB 안에서는 회사코드로 계열회사를 구분할 수 있다. 고객별 JWT 비밀키·업로드·백업도 분리한다. 요청마다 고객 DB를 선택하는 기능은 제공하지 않는다. 개발·테스트 DB는 고객 운영 DB와 별도로 준비한다.

## 2. 메뉴와 화면

| 순서 | 그룹 | 메뉴 |
|---|---|---|
| 1 | 홈 | 업무 진입 링크 |
| 2 | 전자결재 | 결재문서 |
| 3 | 게시판 | 게시글·댓글 |
| 4 | 보전관리 | 설비 마스터, 예방점검, 작업의뢰서, 작업 오더, 허가요청서, 작업허가서 |
| 5 | 구매관리 | 거래처, 구매요청, 구매발주 |
| 5-1 | 재고관리 | 자재 마스터, 창고, 입고, 출고, 타창고출고, 조정, 재고 현황, 수불장, 월 마감 |
| 6 | 조직관리 | 회사 정보, 사업장, 부서 |
| 7 | 사용자·권한관리 | 사용자, 역할별 권한 배정, 로그인 이력 |
| 8 | 공통코드 | 공통코드 관리 |

- 홈·사이드바는 같은 메뉴 정의를 사용한다. 메뉴는 권한과 관계없이 표시한다. 조회 권한이 없으면 해당 업무 화면 대신 안내를 표시하고 자동 조회 API를 호출하지 않는다. 버튼과 최종 API 실행은 각각 권한을 검사한다. 결재·게시판은 별도 모듈 CRUD 권한을 요구하지 않는다.
- 목록 상단은 `인쇄`, `신규`이며 일반 행별 Actions는 두지 않는다. 허가요청 행의 `작업허가`는 업무 연결 버튼이다.
- 개별 화면은 해당 기능에 따라 `인쇄`, `목록`, `저장`, `삭제`, `상신`을 표시한다. 재고전표는 `확정`, 허가요청은 `신청`을 사용한다.
- 시스템 문서번호는 읽기 전용이다. 신규에는 ‘저장 시 자동 생성’을 표시한다. `documentNo`는 지원하는 문서에서 사용자가 선택 입력하는 별도 관리번호다.

## 3. 인증·권한·회사 범위

- 회사코드·사용자 ID·비밀번호로 로그인한다. 인증 이후 회사·사용자·역할·소속·권한은 서버 DB 정보를 기준으로 처리한다.
- 일반 업무는 Controller의 create/read/update/delete 권한과 Service의 회사·작성자·상태 조건으로 제한한다. 결재·첨부·게시판은 CRUD RBAC 예외이며 인증과 회사 분리를 유지한다.
- 문서 범위를 적용하는 예방점검·작업의뢰·작업오더·허가요청·작업허가·구매·재고전표는 회사 전체, 본인 사업장, 본인 부서와 하위 부서 중 사용자 설정에 따른다. 마스터는 회사 단위다. 재고전표·현재고·수불·월 보고서는 COMPANY_ALL에서 회사 전체, OWN_SITE/OWN_DEPARTMENT에서 자기 사업장 범위를 적용한다. 월 잠금은 회사 단위이며 별도 사용자별 창고 권한은 없다.
- 상태가 있는 문서는 작성자만 D 상태에서 수정·삭제한다. 상태 없는 마스터는 모듈 권한으로 관리한다. 게시글·댓글은 각각 작성자만 수정·삭제한다.
- 역할과 권한 배정은 회사별이다. **지원 권한은 백엔드 MODULE_ACTIONS 상수**로 정의한다. 권한 정의 CRUD 화면·API는 없으며 회사별 역할 배정만 관리한다.
- 새로고침 시 서버에서 사용자 정보를 복원한 뒤 화면을 표시한다. 인증 만료는 재로그인하며 통신 장애는 토큰을 보존하고 재시도한다. 미저장 업무 입력은 새로고침으로 복원하지 않는다.
- 로그아웃은 브라우저 토큰·Context를 지운다. 별도 서버 로그아웃·자동 갱신 API는 없다. 비밀번호 변경·관리자 비밀번호 재설정 시에는 기존 JWT를 무효화한다.

## 4. 문서와 공통 처리

- 업무 날짜는 화면에서 YYYY-MM-DD, 년월은 YYYY-MM으로 표시·입력한다. API·저장은 기존 YYYYMMDD·YYYYMM을 유지하며 등록·수정 등 시각은 한국 시간으로 표시한다. 작업허가의 날짜·시간은 해당 업무 형식을 유지한다.

- 문서 ID는 최초 저장 시 `모듈약어-YYYYMM-일련번호`로 발급한다. 회사·모듈·발급월별 증가하며 한국 시간 기준이다. 수정·상신·업무 날짜 변경으로 ID를 다시 발급하지 않는다.
- PMAINT, WRKREQ, WRKORD, PERREQ, PERMIT, PURREQ, PURORD, INVDOC, APPROV는 6자리 약어이며 게시판은 BORD를 사용한다. 일련번호는 5자리이고 월 99999건 초과 시 발급을 중단한다.
- 첨부·품목·댓글 등의 내부 식별자는 UUID를 사용한다. 생성 POST마다 새 문서번호를 발급하므로 응답이 불확실하면 목록에서 저장 여부를 확인한다. 저장 중에는 버튼을 비활성화한다.
- 결재 연계 문서는 D(초안)→P(진행)→C(완결)/R(반려)/X(취소)다. 허가요청은 D→C로 신청 처리하며 일반 재고전표는 초안 없이 C로 확정하고 X로 취소한다. 타창고출고가 자동 생성한 입고만 W(수령 대기) 상태를 거쳐 C로 확정한다. 별도 confirm 권한은 두지 않는다.
- 결재 결과와 원본 동기화는 순차 실행한다. 결재 승인 후 원본 상태 변경 실패가 발생해도 승인 결과를 롤백하지 않는다. 관리자가 로그와 문서번호로 불일치를 처리한다.
- 감사필드는 생성·수정 시각과 사용자이며 서버가 기록한다. `deleteYn`은 감사필드와 별개다. 마스터·문서는 논리 삭제하며 공통코드 항목과 첨부 상세 등 일부 내부 자료는 실제 삭제한다.

## 5. 조직·사용자·공통코드

- 회사 정보는 본인 회사의 명칭·사업자번호·담당자·연락처·비고를 수정한다. 일반 회사 생성·삭제 API는 제공하지 않는다.
- 사업장은 회사별로 관리한다. 부서는 사업장과 독립적이며 상위 부서를 선택한다. 서버는 자기 참조를 거부하며 다단계 부서 순환을 추가 차단하는 로직은 두지 않는다. 현재 부서 화면은 표이고 순환을 표시하는 트리는 미구현이다.
- 창고 식별자는 회사+사업장+창고번호다. 사업장은 필수이며 창고 메뉴는 재고관리 아래에 둔다.
- 창고 삭제는 담당자가 현재고 수량·금액과 해당 창고로 수령 대기 중인 입고 전표를 확인한 뒤 수행한다. 잔고가 남아 있으면 정상 재고 거래로 정리하고, 대기 입고는 수령 확정 등 업무 처리를 완료한 뒤 삭제한다. 삭제 화면은 이 확인 절차를 안내한다. 서버는 삭제 전 잔고·대기 전표를 자동 검사하지 않는다.
- 공통코드·기준정보를 삭제해도 기존 문서의 식별자는 보존한다. 삭제 항목의 명칭은 별도 복원 조회 없이 표시되지 않을 수 있다.
- 사용자 사업장·부서·역할은 활성 선택 목록을 제공한다. 저장 시 기준정보 존재·활성 여부를 별도 재검증하지 않는다. 기준정보 삭제로 기존 사용자 소속·역할 값을 자동 변경하지 않는다. 권한 회수는 역할 권한 배정 변경이나 사용자 변경·삭제로 처리한다.
- `MATL_TYPE` 같은 코드 그룹은 시스템 상수다. 별도 Code 엔티티는 없으며 CodeItem은 회사+codeId+codeItemId로 값·명칭·정렬순서를 관리한다. 같은 항목 코드도 회사별 명칭을 다르게 둘 수 있다.

## 6. 첨부

- 첨부가 없어도 첨부 영역과 빈 목록을 표시한다. disabled에서는 조회·다운로드만 제공한다.
- 파일 선택 즉시 UUID 첨부 그룹에 서버 업로드한다. 신규 문서는 refId=null로 관리하고 최초 저장 후 문서 ID를 연결한다. 첫 첨부를 위해 문서번호를 선발급하지 않는다.
- 업로드·목록 갱신 중 부모 저장·상신·확정을 막는다. 파일 추가·삭제는 문서 저장과 별개로 즉시 반영한다.
- 마지막 파일을 삭제해도 첨부 그룹은 유지한다. 미저장 문서나 DB 실패로 생기는 고아 파일은 허용하며 자동 정리하지 않는다.
- 첨부는 JWT 로그인 후 프런트의 첨부 키를 사용하며, 회사는 전송값과 무관하게 서버 인증 정보로 확인한다. 별도 첨부 권한·작성자·원 호출 모듈 접근 권한은 검사하지 않는다. 회사·첨부 그룹을 확인한 인증 API로 파일을 제공한다. 파일 경로는 서버가 생성하며 사용자 임의 경로를 허용하지 않는다.
- 원본 연계 결재는 원본 첨부를 조회한다. 추가·삭제는 원본 화면에서 수행하며 독립 결재는 자체 첨부를 관리한다.

## 7. 보전관리

| 업무 | 주요 규칙 |
|---|---|
| 설비 | 같은 회사·사업장의 상위 설비를 트리로 선택한다. 자기·자손 참조와 순환을 거부하며 활성 하위 설비가 있으면 삭제·사업장 변경을 제한한다. |
| 예방점검 | 점검일과 설비 주기로 다음 점검일을 제안하고 사용자가 수정한다. 주기가 없으면 빈칸이다. 상세는 항목·기준값·점검값·단위다. |
| PM 상신 | OK/NOK 판정·점검부서·점검자를 확인한다. 결재 C 후 PM의 점검일·다음 점검일을 설비에 그대로 반영한다. |
| 작업의뢰 | Trouble Memo로 작성하고 전자결재로 확정한다. C 의뢰에서 작업계획을 작성할 수 있다. |
| 작업오더 | PLAN/ACTUAL을 구분한다. 계획은 C 의뢰를 선택 참조하고 실적은 완결(C)된 계획을 선택 참조한다. 단독 작성도 가능하다. |
| WO 상세 | 공수·자재·비용을 복수 행으로 입력하며 합계를 서버 계산한다. 계획 복사·원본 첨부 조회를 제공하고 자동 재고 차감은 하지 않는다. |

예방점검 대상·허가 대상 여부와 법정점검 정보는 설비 마스터에서만 관리한다. PM 완료 시 설비 날짜 갱신은 편의 기능이며 기존 날짜와의 선후 비교·역행 방지 조건은 추가하지 않는다. 사용자는 PM과 필요시 설비 마스터에서 날짜를 직접 조정한다. 다음 점검일이 오늘 이전인 PM은 목록에서 표시한다. 결재 본문은 저장된 원본의 최신 내용으로 생성하며 결재 본문 편집은 원본을 변경하지 않는다.

## 8. 작업허가

- 허가요청은 신청자가 D에서 작성·수정하고 신청 시 C로 확정한다. 전자결재를 거치지 않는다.
- 담당자는 신청 완료 요청의 `작업허가` 버튼이나 단독 등록으로 허가서를 작성한다. 일반은 필수이며 화기·밀폐공간·고소·전기·양중·굴착을 추가 선택한다.
- 유형별 안전조치요구·특별요구·안전검토의견을 템플릿에서 복사하여 편집한다. 작업정보, 요구 첨부, 발급자·승인자를 저장한다.
- 작업계획서·위험성평가서의 실제 첨부를 확인하고 상신 화면에서 별도 결재선을 입력한다. 발급자·승인자는 허가문서 입력값으로 결재선과 무관하다. 연계 결재의 저장 버튼은 비활성화하며 상신으로 처리한다.
- 출력은 일반과 선택 특별허가서를 각각 별도 A4 한 장으로 생성한다. 각 페이지에서 개별 자필 서명을 받는다.
- 공통 작업정보, 보충허가 체크, 4열 안전요구·수기 확인, 특별요구·검토의견, 안전조치 확인/작업완료 확인의 날짜·시간·입회자·작업자, 발급자·승인자, 비고와 첨부서류를 포함한다.
- 일반의 가스 측정과 현장 확인·서명은 출력 빈칸만 제공한다. 허가 발행 시 입력값이나 전자 현장 서명으로 저장하지 않는다. 출력 길이를 초과하면 내용을 줄이도록 안내한다.

## 9. 구매

- 자재 마스터는 회사 공통이며 결재 상태 없이 관리하고 첨부할 수 있다. 거래 이력이 있는 자재는 기본단위 변경을 제한한다.
- 거래처는 구매·재고관리에서 회사별 등록·수정·논리 삭제한다. 발주는 등록된 거래처 선택이 필수이며 vendorId만 저장한다. 공급처 정보는 회사와 vendorId로 조회하므로 거래처 선택 변경 및 마스터 수정 시 최신 정보가 표시된다. 거래처 삭제 전 연결 발주 건수를 안내하되 논리 삭제는 허용한다. 삭제된 거래처는 기존 발주에서도 이름·연락처를 별도로 복원해 표시하지 않으며 신규 선택에서도 제외한다. 발주에 저장된 거래처 ID는 유지한다. 결재 본문은 생성 당시 내용을 유지한다.
- 구매요청은 품목·수량만 입력하고 비교 견적은 첨부한다. 단가·금액은 입력하지 않는다. 전자결재 C인 요청만 발주 대상으로 선택한다.
- 구매발주는 단독 작성 또는 완결 구매요청 한 건 참조를 지원한다. 참조는 제목·납기·본문·비고·품목의 초기값을 한 번 복사하는 용도이며 품목 추가·삭제와 수량·규격 변경이 가능하다. 요청이 이후 변경되어도 기존 발주에는 자동 반영하지 않는다. 단가·거래처는 발주에서 입력한다.
- 발주는 refModule/refId로 구매요청 한 건을 선택적으로 참조한다. 같은 요청으로 여러 발주를 만들 수 있고, 기존 발주 상태나 수량으로 차단하지 않는다. allocation·품목 병합·잔여 수량 계산은 사용하지 않는다. 원 요청과 발주 화면에서 연결 발주번호·상태·작성일과 상세 링크를 제공한다. 참조 변경·다시 불러오기는 덮어쓰기 확인 후 복사하고, 참조 해제는 입력 내용을 유지한다.
- 구매요청·발주 목록은 문서번호·관리번호·제목 통합 검색과 서버 페이지네이션을 제공한다. 문서번호·관리번호는 별도 열이며 인쇄는 현재 페이지 대상이다. 요청·입고 작성용 원본 선택 목록은 별도 조회로 전체 완결 문서를 제공한다. 거래처·구매 문서 조회 실패 시 이전 목록을 숨기고 인쇄·페이지 이동을 막는다.
- 요청·발주 모두 전자결재를 사용한다. 금액은 KRW이며 부가세·외화·부분입고는 제공하지 않는다.

## 10. 재고와 월 마감

- 구매 담당자와 본사 자재 담당자는 전사 범위, 사업소 담당자는 사업장+부서 범위로 설정하는 운영 기준이다. 역할·범위는 관리자가 배정하며 자동 생성하지 않는다. 재고에서는 사업장+부서 범위도 자기 사업장 기준이다.
- 입고·출고·타창고출고·조정을 별도 메뉴로 제공한다. 구매와 재고 메뉴 그룹은 분리한다. 모든 메뉴는 표시하고 조회 권한이 없으면 API를 호출하지 않고 안내한다.
- 저장 구분은 기존 IN/OUT/ADJUST와 GENERAL/PURCHASE/TRANSFER를 유지한다. 일반입고·구매입고·출고·조정은 등록 즉시 확정하며 일반 초안·수정·삭제는 제공하지 않는다.
- 재고 전용 상태는 W(수령 대기), C(확정), X(취소)이다. 타창고출고는 확정 출고와 대기 입고를 동시에 생성하고 출발 잔고만 차감한다. 수령 창고를 지정하면 사업장이 자동 설정된다. 같은 사업장 이동도 동일하다.
- 수령 담당자는 자기 사업장의 대기 입고를 확정한다. 실제 입고 전기일과 확정순번·확정자·시각을 기록하고 원 출고의 전체 수량·금액을 그대로 입고한다. 분할·재수령은 없으며 대기 중 품목·금액을 수정하지 않는다.
- 재고는 창고별 수량·금액으로 평가한다. 출고단가는 현재 창고 잔고금액÷잔고수량에서 원 미만을 버려 정한다. 출고금액은 확정 단가×출고수량을 원 단위 반올림한다. 전량 출고에도 같은 공식을 적용하며 남은 단수 금액을 자동 소진하지 않는다. 수량 0·금액 잔액은 보존하고 필요하면 조정 화면에서 정리한다. 개당 금액이 1원 미만이면 단가 0원 출고도 가능하다. 확정 전표의 단가·금액은 이후 거래로 재평가하지 않는다.
- 출고 품목 적요에는 출고 당시 잔고금액·수량, 단가 버림 및 출고금액 계산 내역을 자동 기록한다. 사용자 입력 적요는 보존하고 화면과 인쇄에서 함께 확인한다. 타창고 입고에도 원 출고 적요와 금액을 복사하며 취소 시 다시 계산하거나 적요를 변경하지 않는다.
- 조정은 부호 있는 수량·금액 증감을 각각 입력한다. 두 값이 모두 0인 행은 거부한다. 잔고 수량 0·금액 잔액은 허용하며 평균단가는 표시하지 않는다. 결과 수량·금액은 음수가 될 수 없다.
- 취소는 회사 전체 최신 유효 확정순번부터 원 수량·금액을 역반영한다. 출고 취소 시 대기 입고도 함께 취소한다. 입고 확정 후에는 입고→출고 순서로 취소한다. 취소된 이동입고는 대기로 복원하거나 재수령하지 않는다. 구매입고 취소 후에는 원 구매오더로 다시 입고할 수 있다.
- 발주의 입고 목표 사업장은 유지한다. 구매입고는 완결 구매오더 전체 수량·단가를 사용하며 회사 전체 중복을 검사한다. 일반출고는 입고 참조 원본이 아니다.
- INVDOC read/create/update를 유지한다. 등록·확정·취소는 read도 필요하다. 재고에서 OWN_DEPARTMENT는 OWN_SITE와 동일하게 자기 사업장 범위이며 별도 사용자별 창고 권한은 없다. 타창고출고의 수령지는 회사 내 다른 사업장 창고도 지정할 수 있다.
- stock_balance에서 회사+사업장+창고+자재별 수량·금액만 저장하고 해당 잔고만 증감한다. 평가·수불부·이동 중·월 집계 테이블은 사용하지 않는다. 확정과 취소는 회사 잠금 아래 전표·품목·잔고를 하나의 트랜잭션으로 처리한다.
- 월 Open/Close는 거래 잠금만 관리한다. 전월부터 순서대로 마감하며 후속 마감월 보호는 유지한다. 대기 입고는 마감을 막지 않고 동일·타 사업장 모두 월 이월 가능하다.
- 현재고는 잔고, 수불장은 확정순번에 따른 전표 증감, 월 보고서는 전기일에 따른 기초·기간증감·기말을 조회한다. W/X는 수불에서 제외한다. 수령 전 이동분은 창고 잔고에 포함하지 않는다. 재Open·정정하면 과거 보고서도 바뀔 수 있다.

## 11. 전자결재·게시판

- 결재·합의는 같은 순번 체계로 처리하고 화면 동작은 `승인`으로 통일한다. 현재 미처리 최소 순번만 처리하며 남은 결재·합의자가 없으면 완결한다.
- 참조는 처리 순번에서 제외하고 C 문서만 조회한다. 반려·부동의 의견은 선택이다. P 문서는 상신자가 취소할 수 있다.
- 본문은 Tiptap JSON으로 저장하여 서식을 유지한다. 원본 연계 결재는 저장을 비활성화하고 상신 때 저장한다.
- 게시판은 같은 회사의 사용자에게 게시글·댓글을 제공한다. 결재 상태가 없으며 게시글과 댓글 각각 본인 작성물만 수정·삭제한다. 관리자 역할도 예외가 아니다.
- 삭제되지 않은 댓글이 있으면 원문 삭제를 막는다. 본문 수정은 가능하며 모든 댓글을 각 작성자가 삭제한 뒤에는 원문 작성자가 원문을 삭제할 수 있다.

## 12. 사용자 설정·로그인 이력·입력값 유지

- 상단 사용자 메뉴에서 내 정보 수정, 비밀번호 변경, 로그아웃을 제공한다. 본인의 이메일·전화번호 수정에는 관리자 사용자 조회 권한이 필요하지 않다.
- 새 비밀번호는 영문·숫자를 포함한 10자 이상, UTF-8 기준 72바이트 이내다. 현재 비밀번호 재사용을 거부하고 과거 비밀번호 이력은 저장하지 않는다. 변경 후 모든 기기의 기존 토큰을 무효화하고 다시 로그인한다.
- 로그인 이력은 같은 회사의 조회 권한 보유자에게 시각·사용자·성공/실패·실패 사유·IP·브라우저를 제공한다. 날짜·사용자·결과 검색과 페이지 이동을 지원하며 비밀번호·토큰은 기록하지 않는다.
- 활성 선택 목록에서 삭제된 부서·사업장 등을 제외해도 로그인 사용자에게 남아 있는 소속 기본값과 기존 문서 값은 유지한다. 목록에 없다는 이유로 값을 비우거나 대체하지 않는다. 다만 표시 이름 조회는 deleteYn=N을 유지하며 삭제된 항목을 위한 예외 조회·선택 옵션은 제공하지 않는다. 문서 접근 범위는 기존 활성 부서 트리 기준으로 별도 판단한다.
- 단위는 회사별 UNIT 공통그룹을 사용하며 환산하지 않는다. 우선순위는 프런트의 상·중·하 참고값이고 통화는 KRW 고정이다. 기존 저장값이 선택 목록에 없어도 표시·보존한다.
- 결재선은 제목, 결재선 입력, 본문 순으로 배치한다. 유형을 행마다 선택하고 참조 행은 맨 아래로 정렬한다. 결재·합의와 참조 각각의 입력 순서는 유지한다.
- 결재 A → 참조 C → 합의 B 입력 시 결재 A(1) → 합의 B(2) → 참조 C(3)로 저장하며 참조 순번은 화면에서 —로 표시한다. 상신자는 0번이다. 참조는 승인 완료 후 열람하며 별도 확인 동작이 없다.
- 결재선은 중복 사용자·상신자 본인·다른 회사·비활성 사용자를 거부한다. 상신 시 결재·합의가 한 명 이상 필요하다. 작업허가는 원문 본문을 유지하며 결재·합의·참조는 별도 결재선에서 입력한다.

역할 권한은 모듈을 행, 등록·조회·수정·삭제를 열로 표시하고 각각 독립적으로 체크한다. 지원하지 않는 동작은 —로 표시한다. 체크·해제 후 저장 버튼으로 기존 권한 배정 API에 한 번에 전송한다.

결재 목록은 문서함·상태·문서번호/관리번호/제목/상신자 ID 통합 검색을 서버에서 적용하고 20건씩 조회한다. 목록 인쇄는 제공하지 않고 상세 문서 인쇄는 유지한다. 원문 상태 반영이 실패해도 결재 결과는 유지하고 원문 반영 실패 안내를 표시한다. 별도 재반영·시스템 복구 기능은 추후 검토한다.

예방점검은 점검일을 오늘(한국 날짜)로 기본 입력하고 사용자가 수정할 수 있는 필수값으로 관리한다. 점검 주기·단위는 설비 마스터 값을 읽기 전용으로 표시하며 다음 점검일은 제안 후 사용자 보정이 가능하다. 목록은 문서번호·관리번호·제목·설비번호 통합 검색과 서버 페이지네이션을 제공하고 상태·판정·점검일 검색 필터는 두지 않는다. 목록 인쇄는 현재 페이지 자료를 출력한다.

작업의뢰·작업오더 목록은 문서번호·관리번호·제목·설비번호 통합 검색과 서버 페이지네이션을 제공한다. 상태·긴급도·기간·계획/실적 필터는 제거하고 목록의 관련 표시는 유지한다. 시스템 문서번호와 관리번호는 각각 별도 열로 제공하며 목록 인쇄는 현재 페이지를 대상으로 한다.

허가요청·작업허가 목록은 문서번호·관리번호·작업명 통합 검색과 서버 페이지네이션을 제공하며 직접 입력하는 설비번호는 검색하지 않는다. 문서번호·관리번호를 각각 표시하고 목록 인쇄는 현재 페이지를 대상으로 한다. 삭제된 발급자·승인자의 ID는 유지하지만 활성 사용자 목록에 없으면 별도 이름 표시나 기존 선택 옵션을 제공하지 않는다. 허가요청 상세 인쇄는 한글 항목명을 사용한다.

업무문서 소속 입력: maintenance·구매의 사업장·부서는 신규 작성 시 로그인 소속으로 초기화하고 프런트에서 읽기 전용으로 표시한다. 기존 문서와 원본 참조 시 작성 문서의 소속을 유지한다. 입력 소속을 scope와 비교하는 저장 검사는 제거하되 대상 문서와 참조 원본의 조회 scope는 유지한다. 구매발주의 입고 예정 사업장(toSiteId)은 필수 선택값이며 발주 소속 사업장과 다를 수 있다.

## 수량·단가 입력 및 표시

구매·재고·작업오더 자재의 신규·변경 수량은 소수점 최대 2자리, 단가는 정수로 입력한다. 표시 기준은 백엔드 numericPrecision metadata를 사용한다. 기존 고정밀 수량과 작업오더 JSON의 미변경 값은 보존하며 표시 반올림으로 저장 원본을 덮어쓰지 않는다. 품목 단가 Entity는 정수이고 재고 평균단가는 잔고에서 원 미만 버림으로 계산한다. 출고는 이 단가에 수량을 곱하며 수량 DB 정밀도는 유지한다. 공수는 기존 4자리 기준을 유지한다.

## 13. 유지 정책과 미구현 범위

- 창고 삭제 정책 강화, 추가 인덱스·실행계획 최적화, 부서 순환 트리 표시는 후속 검토 대상이다.
- 전월에 한한 임시 Open 제한은 추가하지 않는다. 현재 월 Open/마감 해제와 마감 순서를 사용한다.
- 고아 첨부 자동 정리, 첨부 원문별 추가 권한, 결재 원문 재동기화 도구는 제공하지 않는다.
- 원문 연계 결재는 상신 시 저장하고 별도 임시저장 버튼을 제공하지 않는다. 단독 결재는 임시저장이 가능하다.
- 첨부 연결 실패·표시 잔존 등 기술적 미결정 사항은 [기술 명세의 후속 검토](tech_spec.md#15-후속-검토와-운영-한계)를 따른다.
