# Database Specification for new-cmms

## Overview

This document defines the database table and field structure for new-cmms.

Product behavior, user workflows, and scope are defined in `docs/prod_spec.md`.

## Common Database Rules

- All business tables include `companyId`.
- Primary keys are marked in the `contraint` column.
- Foreign key relationships are controlled by the application layer. Database-level FK constraints are not required at this stage.
- Child/detail tables use `itemNo` consistently as the line number within the parent document or group.
- Header tables include the audit fields `createdBy`, `createdAt`, `updatedBy`, and `updatedAt`, and a `deleteYn` soft delete flag declared per table.
- Child/detail tables that are hard deleted (Role Permission, Code Item, Approval Step, Attachment Item) have neither audit fields nor `deleteYn`.
- Document ids are UUIDs generated by the client when the user clicks New, and are never shown. `documentNo` is a separate user-managed text field. Other modules link to a document with `refModule` and `refId` (the document UUID).
- Document status values are `D` draft, `P` progress, `C` confirm, `R` reject, and `X` cancel.
- Only draft documents can be updated or deleted in the service layer.
- Process document headers (Preventive Maintenance, Work Order, Work Permit, Purchase Request, Purchase Order) use a single `status` column, `requesterId`, and no `approvalId`; the approval link is stored on the approval (`refModule`, `refId`) and approval actions update the document `status`.
- Item/detail tables and work permit template JSON fields for these documents are planned and not yet implemented.

## Attachment

Attachments use a common attachment header and attachment item model.

The owning module table stores `attachmentId` as the primary relationship to attachments.

`refModule` and `refId` in the attachment header are required and must match the owning document.

Physical files are stored in local storage with MinIO-compatible object storage support.

Maximum file size and allowed file types are controlled by `.env`.

### Approval Step

Approval step stores each approval line/action.

Example step definitions:

- `0`: `SUBMITTER`, status `Y` after submit
- `1`: `APPROVER`, status `Y` approve or `N` reject
- `2`: `REFERENCE`, status `Y` after submit
- `3`: `APPROVER`, status `Y` approve or `N` reject
